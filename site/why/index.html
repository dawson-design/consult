Understand your code again

METR is a research group that evaluates AI models. In August 2026, it disclosed that one of its researchers had put an AI-built app online behind a Google login. A flaw in the code quietly switched the login off. An attacker got in, took an API key, and over about three weeks ran up around $600,000 in model usage. The app was meant to be protected. The code did something else.

If people who evaluate AI for a living can miss that, anyone can. Agents now produce code faster than anyone can absorb it, and failures like this one hide in the gap. Consult turns your agent into an expert you consult. It plans each change with you, builds in small tested steps, has the work checked, and walks you through the result. You give up a little speed, and you get code you can explain.

A mile wide and an inch deep

Agents let you ship more, and the pressure to ship comes from your team, your manager, or yourself on a side project. As the code grows, the share of it you understand shrinks. If you arrived after the foundations were laid, you also never learned why the code has its shape. Your understanding ends up a mile wide and an inch deep, and you can drown in two inches of water.

In Programming as Theory Building (1985), Peter Naur argued that a program is a theory held in its builders’ heads, and the code records only part of it. The theory is what lets you change a program safely: why it is shaped this way, and what breaks if you move a piece. When an agent lays the foundations, its theory ends with the session, and unless you were there, you never form one of your own.

A small Anthropic study suggests the cost. Among 52 mostly junior engineers, those who learned a new library with AI scored 50% on a quiz about it, against 67% for those who coded by hand. The biggest gap was in debugging, the skill you need when code behaves differently from how you believe it does. The METR incident had its own causes, but it shows how expensive that kind of wrong belief can get.

An expert to consult on every change

It does not have to go this way. The central finding of Google’s 2025 DORA research is that AI amplifies what a team already has. With good tests and fast feedback, AI makes you faster. Without them, you ship more change, and more of it breaks.

How you use the agent matters too. In the Anthropic study, engineers who asked the AI questions and had it explain its code scored 65% or more, about the same as those who coded by hand. Those who handed it the whole task scored below 40%. The groups were small and the study cannot prove cause. Still, it points to a practical choice: treat the AI as an expert to consult.

That idea gave Consult its name. A frontier agent has read more about software engineering than any one person could. Consult distils that knowledge to what high-quality engineering needs and writes it into the agent’s skills, so it applies to every change. It then brings that knowledge to you as a conversation.

The north star: Simple Made Easy

In Simple Made Easy, Rich Hickey separates two words we use as if they meant the same thing. Simple means not tangled together: one role, one concept, one job. Easy means close at hand and familiar. Easy things can still be complex, and simple things can take work to reach.

Code spreads wide when easy wins over simple, and agents excel at easy. They learned from vast amounts of public code, so they reach first for the pattern they saw most, which may not be the best one. Copying a rule is easy. Giving it one home is simple, but it takes a decision about where the rule belongs, and agents skip that step.

So the rule Consult puts above every other, in every session, is its Iron Law: Complexity is the enemy: keep software simple enough to understand, change, and prove. Much of the rest follows from it. Keep unrelated parts separate. Make state and effects explicit. Build only what was asked for. Before adding a layer, name what it couples to.

Defaults that suit agents

A consultant who answers every question with “it depends” is no use. Neither is an agent left to choose, which falls back on the most common pattern. Consult picks a default for the choices every project faces, based on what works best when an agent writes the code and a person has to understand it. In an existing codebase it follows what the project already uses. On new code, it starts here.

Group by feature

A feature’s data, rules, and tests live together, instead of spreading across controller, service, and repository folders. The agent, and you, can find one behaviour in one place and change it without touching the rest. A layer has to justify itself with a real boundary, such as a separate process, deploy, or trust boundary.

Tests that read like specs

Left alone, an agent tests that its code runs, not that the feature works, and tests written by reading the code tend to confirm its bugs. Behaviour-style test libraries, such as RSpec for Ruby and Vitest’s describe and it for TypeScript, make each test state what the feature should do for its user. The test fails when the feature is wrong, and you can review the tests as a list of requirements.

Frameworks with less to write

On a new frontend, Consult starts from a framework with the basics built in, such as Svelte, which includes scoped styles, transitions, and reactive state. Fewer add-ons should mean less for the agent to write and for you to review. This default is a judgement call, and a project that already uses React stays on React.

The API spec comes first

You and the agent write the OpenAPI spec ahead of the handler, which settles the contract while it is cheap to change. New resource APIs default to JSON:API, because it already answers questions an agent would otherwise improvise for each endpoint, such as response shape, pagination, and error format.

Start from a design system

An agent left to style a screen invents one-off values. Consult starts from the product’s own design system, or an established one such as IBM Carbon when there is none, so every screen uses the same tested components.

One tool per job

Use uv for Python, and the framework’s own bundler for TypeScript. Every extra tool is more configuration for the agent to get wrong and for you to check.
