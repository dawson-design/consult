What the eval shows

Consult asks the agent to prove what a change claims. We build Consult the same way: the rules we can measure are scored against bare Claude Code, a rule that changes nothing is cut, and a failure becomes a rule fix that is then rerun.

Claude Code built the same project with and without Consult, five attempts each, on 4 November 2026. Every number here comes from the results file, and you can rerun the eval harness yourself.

The code stays simple as the project grows

The project is a complex service, built up over five stages the way you actually build with agents: each stage adds features to the code the last one left. After each stage, a code analyzer scores simplicity from 0 to 1. The score averages five shares: functions short and flat enough to read in one pass, decisions in pure functions, state kept apart from logic, imports without cycles, and interfaces with more than one implementation.

Consult writes about twice as many lines, but each part of the score is a share, so more code doesn’t lower it by itself.

Five of these scores showed no lift, so their rules have since been cut: core rule 3 (libraries), core rule 6 (untrusted input), default 11 (tooling), default 15 (comments), and the self-review ban that opened human rule 6. The untrusted-input and tooling checks still run as readouts, so the next run shows whether the cuts cost anything.

What it costs

Consult used 2.1 times the output tokens and 2.2 times the agent time of bare Claude Code. Its first version used about five times the tokens and scored no better, which is why it was rebuilt.

Room for improvement

We change Consult and measure it all the time. Sometimes a change that helps one part sets another back. Each update is scored against these results, and the next one works on what fell short.

Across two runs, 2 of 8 staged builds with Consult failed, both the same way: the agent added a required setting nobody asked for, and the server stopped starting.

In one, a generic “Approved. Continue.” was taken as a yes to extras proposed a stage earlier. In the other, the agent recommended an access token, and the scripted reply, “Use your recommended option for anything still open”, accepted it. Consult’s core now limits a generic approval to the plan just shown, and offers unrequested settings only as opt-ins. In three more staged builds with those rules, all passed and none added an unrequested setting.

The token failure is why the overall task reward shows no lift (−0.06, within noise): in the five-attempt run, Consult passed the staged project 4 times out of 5, against 5 for bare.

How it was measured

Both arms ran Claude Code 2.1.282 with Claude Opus 5.5 at extra-high effort in sandboxed Harbor trials, with the same prompts and scripted replies. Code analysis, the transcript, and a probe that runs the finished app produce every score but two: a language model judge reads the code for core rule 3 and default 15, with no weight in the task reward. The rule scores come from rescoring the same saved attempts with the current checks. The check for unrequested environment variables (core rule 2) is left out, because it misses settings read through a schema. The remote-calls score (default 9) uses the probe as it was then, which counted a retry the brief never asked for as a pass; the probe now gives full marks to a timeout without a retry.

Limits: five attempts per arm, one five-stage TypeScript project plus a control, and a simplicity score we defined. The eval image had no git identity, so Consult’s commits failed and the commit rules score each attempt to commit. The measured version predates the opt-in rule and a proof rule that prefers spec-style test libraries.
